# Как помочь RustyCord

🇷🇺 Русский · [🇬🇧 English](CONTRIBUTING.en.md)

Спасибо, что заглянули! RustyCord делает один человек в свободное время, поэтому каждая пара рук здесь на вес золота. Этот документ нужен, чтобы вы тратили меньше времени на догадки, а я меньше на переспрашивание.

**Сразу о главном:**
- Денег нет. Есть спасибо, ваше имя в [CHANGELOG](CHANGELOG.md) и внимательное ревью.
- Времени у меня мало. Отвечаю обычно **раз в одну-две недели**, иногда бывают паузы дольше. Это не значит, что вас игнорируют, просто основная работа съедает почти всё.
- Читайте [CODE_OF_CONDUCT](CODE_OF_CONDUCT.md): уважаем друг друга, без политики, без национальных оскорблений.

---

## Выберите свою роль

- 🦀 **Rust-разработчик.** Самая нужная помощь: голос и songbird, Gateway, декодеры, баги, с которыми автор не справился.
- 🧪 **Тестер / QA.** Код не нужен: пройдитесь по приложению и выпишите баги списком. Отдельный человек на эту роль очень нужен.
- 🎨 **Svelte / дизайн.** Внешний вид сейчас один большой баг.
- 🐧 **Linux / macOS / Windows 10.** Просто запустите сборку и расскажите, что получилось.
- 🔬 **Реверс протокола.** Сверка с официальным клиентом, документация.

---

## Что мы принимаем, а что нет

**Принимаем** то, что улучшает жизнь пользователю: исправления багов, стабильность, удобство, новые QoL-функции. Мерило простое: *функция помогает человеку, а не делает что-то за него от имени аккаунта.*

**Не принимаем и закрываем без обсуждения:**
- селфботов, массовую рассылку, автоматизацию действий от имени аккаунта;
- обход защиты Discord, антифрода, капчи и ограничений;
- любую отправку токена и пользовательских данных куда-либо, кроме серверов Discord;
- функции, цель которых скрыть клиент от Discord или выдать за официальный.

Простые QoL-идеи часто лучше делать как **плагин** (см. [`plugins/`](plugins)), а не вшивать в ядро. Если не уверены, где место вашей идее, откройте обсуждение в Discussions, прежде чем писать код.

## Как собрать и запустить

Нужны [Node.js](https://nodejs.org) ≥ 20, [Rust](https://rustup.rs) ≥ 1.77 и системные библиотеки Tauri:

- **Ubuntu/Debian:** `sudo apt install libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev libasound2-dev libopus-dev cmake`
- **macOS:** Xcode Command Line Tools.
- **Windows:** [WebView2](https://developer.microsoft.com/microsoft-edge/webview2/) и [MSVC Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/).

```bash
git clone https://github.com/VinylRUS/Rustycord.git && cd Rustycord
npm install
npm run tauri dev
```

Подробные логи:

```bash
# Linux / macOS
RUST_LOG=debug npm run tauri dev

# Windows (PowerShell)
$env:RUST_LOG="debug"; npm run tauri dev
```

Демо-режим без входа в аккаунт: `npm run dev` и откройте `http://localhost:1420`.

## Проверки перед PR

CI запускает те же команды, так что прогоните их у себя. PR с красным CI мы не рассматриваем (точные флаги смотрите в [`.github/workflows/ci.yml`](.github/workflows/ci.yml)).

```bash
cd src-tauri
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test
cd ..
npx svelte-check
npm run build
```

## Правила для pull request

1. **Один PR, одна проблема.** Маленькие правки ревьюить и сливать легко, большие переписывания лежат месяцами.
2. **Крупное сначала обсудите.** Для всего, что больше пары десятков строк или меняет формат событий, сначала откройте issue или обсуждение.
3. **Не ломайте потребителей.** Если меняете формат события или IPC-команды, проверьте, кто их читает на стороне Rust и на стороне Svelte.
4. **Добавляйте тест**, если чините баг, который можно воспроизвести тестом. Регрессию, пойманную один раз, лучше закрепить навсегда.
5. **Не гасите ошибки ради «стабильности».** Ошибка должна быть видна в логе, но **без токенов, cookie и authorization-заголовков**.
6. **Опишите, что проверили руками**: на какой ОС и что именно вы нажимали.
7. **Никаких задержек, повторов и массовых подписок «наугад».** Любой лимит должен опираться на протокол и измерения.

### ИИ-код

Код, написанный нейросетью, **допустим**, если:
- CI зелёный;
- вы понимаете, что в нём написано, и можете объяснить это ревьюеру;
- в описании PR вы отметили, что использовали ИИ, и коротко написали, что проверили руками. Это не запрет, а подсказка, куда смотреть внимательнее.

## Чувствительные места

Изменения в этих областях проходят ревью у владельца проекта всегда, даже от доверенных мейнтейнеров (см. [`.github/CODEOWNERS`](.github/CODEOWNERS)):

- вход и хранение токена;
- REST-клиент и Gateway;
- система плагинов;
- права и конфигурация Tauri (`tauri.conf.json`, capabilities);
- workflow'ы CI и релизы.

## С чего начать

> Это кандидаты, собранные из разборов и логов. Прежде чем браться, проверьте в текущем коде, что проблема ещё актуальна. Мейнтейнер превратит нужные пункты в issue с метками `good first issue` и `help wanted`.

**Rust**
- Голос: убедиться, что у songbird зарегистрирован PCM-декодер (`symphonia-codec-pcm`) и что передача микрофона реально доходит до собеседника. Добавить тест, который проверяет живой трек в songbird, а не только захват с устройства.
- Gateway: сбрасывать backoff после успешной сессии; ограничитель повторных IDENTIFY при серии 4002; валидация сырых кадров из «консоли протокола»; логирование последних исходящих кадров (без секретов) при закрытии соединения.
- Список участников: регрессионный тест на смену канала внутри гильдии со скрытым списком.
- Токен в системное хранилище (Keychain / Credential Manager / libsecret) вместо `localStorage`.

**Svelte / фронтенд**
- Пересылка ошибок фронтенда в лог с ограничением частоты (первые N с полным стеком, дальше счётчик), чтобы спам не заглушал остальное.
- Внешний вид: сначала составить список проблем, потом чинить.

**QoL-идеи**
- Закреплённые чаты поверх списка.
- Единый список непрочитанного по всем серверам.
- Свой порядок и группировка каналов.
- Поиск по локальной истории.

**Тестеры**
- Запустить сборку на Linux, macOS или Windows 10 и описать, что работает.
- Полный проход по интерфейсу с баг-репортами.

## Как писать баг-репорт

Используйте шаблон при создании issue. В нём нужны:
- версия RustyCord и операционная система;
- что вы делали, что ожидали и что получили;
- лог, запущенный с `RUST_LOG=debug` (см. выше).

**Перед отправкой проверьте лог:** удалите токен, если он там оказался. Идентификаторы и session id можно оставить, но если сомневаетесь, замените их на `<redacted>`.

## Сроки

- Ответ на issue и PR: обычно **раз в 1–2 недели**.
- Issue без активности могут быть закрыты через месяц. Если проблема ещё актуальна, напишите, и мы откроем её снова.
- Уязвимости: **не в публичные issues**, а по инструкции в [SECURITY.md](SECURITY.md).

## Мейнтейнеры

Права на слияние (write access) получают те, у кого есть **несколько принятых PR за разные периоды времени** (не пачка за один вечер) и кто показал аккуратность, особенно в чувствительных местах. Ограничители остаются: защита ветки `main`, обязательное ревью, CODEOWNERS на критичные файлы, ключи подписи и секреты CI только у владельца, двухфакторная аутентификация у всех с доступом.
